2. Design decisions

Things an interviewer is likely to ask about.

Why separate collections, not embedded arrays?

  • Bids can grow without limit; embedding them in the RFQ doc would keep growing it (16MB doc limit) and every bid would rewrite the big doc.
  • Bids and logs are written very often and read on their own (sorted lists).
  • Small RFQ doc = fast listing page.

Three close times on RFQ

  • bidCloseTime - what buyer entered, never changes (for audit).
  • currentCloseTime - moves forward on every extension.
  • forcedCloseTime - hard limit. Extension = min(current + Y, forced).

Computed, not stored

  • Status (Upcoming / Active / Closed / Force Closed) is calculated from time on every read, so no cron job is needed to close auctions.
  • Ranking (L1, L2...) is built from bids each time, so it can never go out of sync.

Stored for speed (denormalized)

  • lowestBid, totalBids, extensionCount live on the RFQ so the listing page needs only one query.
  • lowestBid is updated with $min → atomic, safe with parallel bids.

Indexes

  • rfqs.referenceId unique.
  • bids { rfq: 1, createdAt: 1 } - "all bids of this RFQ".
  • activitylogs { rfq: 1, createdAt: -1 } - latest activity first.

Bid history is kept

  • Each new bid is a new document (never updated). Gives full history for audit.
  • Total amount = freight + origin + destination, saved once so we can sort on it.

3. How L1 / L2 / L3 is derived from the bids collection

This is buildRanking() in utils/auctionHelper.js.

  1. 1. Fetch all bids of the RFQ (sorted by time)
  2. 2. Keep only the latest bid of each carrier (older ones are ignored)
  3. 3. Sort by totalAmount, lowest first (tie → whoever bid first)
  4. 4. Position = rank → index 0 is L1, index 1 is L2 ...
